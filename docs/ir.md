# The IR between the checker and the native backend

Status: the data, the lowering of the first subset and a text form exist (`stage1/ir.bastio`, `stage1/irdump.bastio`, golden tests in `tests/ir`), a register allocator for it (`stage1/irra.bastio`, golden tests in `tests/ra`) and an x86-64 emitter (`stage1/irx86.bastio`, behind `--backend native-ir`); the default backends do not use it yet. Tracks [#125](https://github.com/yukikotani231/bastiolang/issues/125), and is the base of #126 (register allocation), #127 (optimizations), #128 (vectorization), #124 (AArch64) and #129 (native as default).

## Why

`stage1/x86.bastio` (about 9,600 lines) writes assembly in one pass over the checked tree. Everything it knows about a value, it decides while walking: whether a variable lives in a register (`x86_assign_regs`, a pre-pass over the tree that counts uses), where a struct's words sit, what is left in `%rax`. A peephole pass cleans up after it. The items still open in the ROADMAP's native-backend entry (results built in registers, struct fields in registers, more argument registers, vectorization) all need to ask questions of the whole function (which values are live together, which loads repeat, which stores are dead), and a tree walk that has already written text cannot answer them.

Measured today (valgrind instructions, native over C, ROADMAP "Performance"): sieve 1.00, tree 1.17, utf8 1.33, vec 1.26, der 1.21, sum 1.24. The remaining gaps are exactly the ones above.

## Shape

One IR function per Bastio function instance (after `mono`), after verification, with ghost code (`spec`, `ghost`, `assert`, `requires`/`ensures`, loop invariants) already erased. Three-address code on virtual registers, in basic blocks:

- **Values** are 64-bit virtual registers (`v0`, `v1`, ...). Every sized integer is kept widened to 64 bits with its type's width recorded on the operation that can wrap (`wrap_add`, `wrap_mul`, casts); the proofs already guarantee that plain `+`, `-`, `*` do not overflow, so those need no normalisation. This is the one place the IR uses what the verifier proved: the backend never emits an overflow check, and now it also never emits a truncation it does not need.
- **Memory** is explicit: `load.w`, `store.w` (w = 1, 2, 4, 8 bytes) on an address that is a virtual register plus a constant. Frame slots, `Buf`/`Bytes`/`Vec` elements, `Box` and `Str` bytes are all addresses.
- **Blocks** end in `jmp`, `br v, then, else` or `ret`. `loop` and `while` lower to a header block with the exit test. `match` lowers to a `switch` on the enum tag.
- **Calls** take their arguments in virtual registers and return up to two words in registers (as today); bigger results are written through an address.
- **Not SSA at first.** Virtual registers may be assigned more than once. Building SSA (with block parameters rather than phi nodes) is a second step, taken only if the passes of #127 need it; a first allocator and constant folding work without it, and not requiring it keeps the lowering a straight walk of the tree.

Proof-derived facts are carried as annotations rather than as operations: a `load` or `store` that the proofs showed in bounds is simply a plain `load`/`store` (as in the C backend); #127 may later attach ranges and no-alias facts to values so a pass can use them.

## Scalar replacement

A struct or enum value whose address is never taken (never passed as `&`, never in an `&mut` borrow that outlives the statement, never stored through a `Buf`) is split into one virtual register per word at lowering time. Its fields are then ordinary values. Everything else stays in a frame slot. The checker already computes, for the register pre-pass, which names are borrowed or reassigned (`x86_borrows`, `x86_assigned`, `x86_lends`); the lowering reuses those answers instead of re-deriving them.

## Backends

`x86.bastio` becomes three parts: lowering (tree to IR, target independent), the register allocator (linear scan over live intervals, with the existing priorities as the first heuristics), and the emitter (IR to x86-64 text). The emitter is the small, target-specific piece, so AArch64 (#124) is the same IR with another emitter and its own allocator parameters (registers, calling convention).

## Getting there without a flag day

The backend is the compiler's largest file, covers the kernel and user targets (locks, device access, `smp_run`, the pool and page-table builtins, about 5,000 of its lines are builtins), and is compared byte for byte with stage0 by `asmdump --stage0` for the part it shares. A rewrite that has to cover all of it before anything runs would be unreviewable. So:

1. **Per-function fallback.** The new path lowers one function; if it meets a node it does not handle yet, it says so and that function goes through the existing generator. Both emit into the same assembly file with the existing calling convention, so mixed output links and runs. `difftest.sh` already builds and runs every `tests/pass` program, so each step is checked on the whole corpus.
2. **First subset:** integer and bool locals, control flow, calls of up to four words, `Buf`/`Vec` element access, structs of scalars. That is the code `bench/` measures and the part of the kernel that is not a builtin.
3. **Measure before widening.** `bench/run.sh` prints native against C; a step lands only if no `bench/` program is slower and the instruction counts do not rise. The done condition of #125 is exactly this, for all programs, with no function left on the old path.
4. **Then** builtins, `Lock`/device/SMP forms, and the removal of the old generator; stage0's native backend stays as the reference for the part it covers.

## Where it stands

`stage1/ir.bastio` has the operations, `ir_lower` (one function instance to IR, or the first reason it is outside the subset), a pass that drops code no jump reaches, and `ir_print`. `irdump FILE` prints the IR of every function of a program; `tests/ir.sh` compares it with `tests/ir/*.expected`. The subset so far is integer, bool, `Buf` and `Bytes` parameters, locals and results (a buffer is two registers, data address and length; `len`, `blen`, `get`, `bget` and `b = set(b, i, v)` / `bset` become `len` reads, `load` and `store` in place); arithmetic, comparisons, `&&`, `||`, `!`, unary `-`; `let`, assignment to a variable, `if`, `while`, `return`, and calls of non-generic functions of the same kinds. The `wrap_add`, `wrap_sub` and `wrap_mul` builtins lower to the plain operation (the emitter truncates to the type). `alloc`/`balloc`, `free`/`bfree`, `print`, `cast[T]` and `wrap[T]` lower to `alloc`, `free`, `print` and `wrap` (a `cast` is a `mov`: it is proved to fit). The `sieve` and `sum` benchmarks lower completely. Structs are split into registers (scalar replacement): a struct value is its fields' words in consecutive registers, so literals, field reads, field assignment, struct parameters and results of up to two words need no memory. A `Vec` of one-word elements lives in a three-word header (length, capacity, data address) in memory, in a frame slot (`slot`) or in the caller's (an `&mut Vec` parameter is its address; a `Vec` or `&Vec` parameter arrives as three words and is stored into a slot). `vec_len`, `vec_get`, `vec_set`, `vec_push` (with `vgrow` when full) and `vec_free` lower to header loads, element loads and stores. The `vec` benchmark lowers completely. An enum is its tag then the words of its largest payload, in consecutive registers like a struct; variants, `is` and `match` (the scrutinee is copied, a binding copies the payload) lower to tag compares and branches. A struct or enum lent by `&mut` (or by `&` when it takes four words or more) stays in memory as a *place* (a base register and a word offset, in the layout of `x86_words`): scalar, buffer and Vec fields are loaded and stored where they are used, nested structs are places again, and a field is lent on by address. A struct that arrives in words but has a Vec in it is stored to a frame slot and is a place there. A `Str` is held like a `Bytes`: `slen`, `sget`, literals (`str`, sharing the generator's string table), parameters, results and fields. A result of more than two words (a Vec, a wide struct or enum) goes through space the caller reserves: `ret regs a, b, ...` writes the words held in registers (a wide struct or enum built in place) straight to it, `ret mem` copies them from an address (a Vec), `callm` leaves it in a frame slot. Vecs of elements of several words (`vec_get`, `vec_set`, `vec_push`, `vec_pop`, `vec_swap`) are read and written as places at the data address plus the index times the element's words. A `&mut Buf` or `&mut Bytes` parameter arrives as the address of the buffer's two words (length, then data): the function loads them into registers on entry and writes them back before every return, since it may replace the buffer; a caller that lends a buffer puts its two words in a frame slot and reads them back after the call. `set` and `bset` (`bset(&mut b, i, v)`) store into the buffer in place. Generic enums, structs and functions lower as the instances the monomorphizer made: `Option[u64]::Some(x)`, `Pair[A, B] { .. }` and `f[T](..)` take the instance of their type arguments. `bcopy` is a forward byte loop (`load` and `store` of one byte), and `bfrom` allocates the bytes and copies the literal into them the same way. A struct with a Vec in it (`Bits`, a hash map) is kept in a frame slot as a place: a literal is built there, a `let` copies into a slot of its own, and as a result it goes through `callm` / `ret mem`. Not yet: `&mut` of scalars, `vec_push_within`, `vec_try_reserve`. The IR is not in SSA form and has no blocks as such, only labels; the register allocator and the emitter come next.

## Register allocation

`stage1/irra.bastio` splits the instructions into basic blocks, computes liveness by backward dataflow (the registers are not in SSA form, so a register assigned in a loop is live around the whole loop), gives each register one interval from its first to its last position, and runs a linear scan over the intervals in order of start. There are two pools: callee-saved registers, which survive calls, and caller-saved ones. An interval that is live across a call (`call`, `alloc`, `free`, `print`, `vgrow`) takes a callee-saved register; any other takes a caller-saved one first. When both pools are empty the register goes to a frame spill slot. The emitter keeps a few registers for itself, so the pools handed to the allocator are the rest. This first version does not weigh uses by loop depth or evict an interval for a hotter one; `tests/ra.sh` shows how often it spills over the corpus (about 2 percent of registers with 5 + 6 machine registers) so a better rule can be measured against it. `ra_valid` recomputes the intervals from the instructions and checks that no two registers that are live together share a machine register and that none that is live across a call sits in a caller-saved one; `tests/ra.sh` runs it over `tests/pass`, `bench` and `core`.

## Passes

`stage1/iropt.bastio` holds the passes that run between the lowering and the allocator. The first is scalar replacement of frame slots (`iropt_slots`): a `slot` whose address is only the base of one-word `load`s and `store`s at constant indices is dropped, each of its words becomes a virtual register of its own, a `store` becomes a `mov` into it and a `load` a `mov` out of it. A `Vec` parameter, which the lowering stores to a slot so the `vec_*` forms can address its header, then keeps its length, capacity and data address in registers instead of reading them from the frame at every `vec_len` and element access. A slot whose address goes anywhere else (a call, `vgrow`, `ret`, arithmetic, a store) stays in memory. The second pass is copy propagation (`iropt_copies`): in `d = mov a` where `d` and `a` are each written once, every read of `d` becomes a read of `a` and the `mov` is dropped (the word registers the first pass creates for a parameter are the main case). It does so only when `a` keeps its value until the last read of `d`: `a` is a parameter, or its definition lies before the `mov` with no label between that definition and the last read of `d`, so a loop that re-runs the definition or skips the `mov` blocks it. The third is jump threading (`iropt_thread`): when `br r, T, F` leads to a label whose first instruction is `br r, T2, F2` on the same register, the outcome is known on that edge and it goes straight to T2 or F2 (the second test that `&&` and `||` leave after materialising their result). Before these runs inlining (`stage1/iropt_inline.bastio`, `iropt_inline`): a `call` or `callm` of a function that lowers, is not the function itself and has as many parameter words as the call has arguments is replaced by the callee's instructions (itself run through the three passes) when the callee has at most 40 instructions, or at most 160 when the call lies in a loop. The callee's registers, labels and argument positions are shifted past the caller's, its parameters become `mov`s from the argument registers, and each `ret` becomes moves into the call's result registers (for a `callm`: one-word stores into the frame slot it named) and a jump to a label after the copy; so a struct or enum that the callee builds in registers stays in registers at the call site. Copies are scanned again for calls, three rounds deep. `irdump --opt FILE` prints the IR after the passes; `tests/ir/NAME.opt.expected` is compared by `tests/ir.sh`. The x86-64 emitter runs the passes, inlining included; the AArch64 one does not yet.

## Emitting x86-64

`stage1/irx86.bastio` is the emitter, reached with `bastioc1 --backend native-ir` (not listed in `--help`; hosted target only). `x86_program_ir` is `x86_program` with one difference: each function is lowered, and a function the IR covers is written from the IR and its allocation; any other goes through the generator of `x86.bastio`, into the same file with the same calling convention, so the two kinds call each other. The convention is the generator's: up to four words of arguments in `%rdi %rsi %rdx %rcx` counted from the last parameter's first word (more are pushed, the last parameter nearest the return address), a result of one word in `%rax` and of two in `%rax:%rdx`, `%r8`-`%r11` clobbered (the callers save theirs), `%rbx` and `%r12`-`%r15` preserved. A `Buf` or `Bytes` is (length, data address) there and (data address, length) in the IR, so the emitter swaps the two at parameters, arguments and results. A function whose parameters or calls disagree with the generator's word counts, or with more than 3000 instructions, stays with the generator.

The allocator is given `%rbx %r12`-`%r15` and `%r8`-`%r11`; `%rax %rcx %rdx %rsi %rdi` are the emitter's, so no value shares a register with an argument. Registers written once, by a constant, get no register and are used as immediates (`ra_alloc_const`); a register may take the machine register of one whose last use is the instruction that writes it, because the emitter reads every operand before it writes. The emitter also copies a temporary into its variable directly (`t = op ...; s = mov t`), divides by a constant as the generator does (`x86_div_const`), repeats a loop's test at its end, and fuses a comparison with the branch that alone reads it. Plain `+`, `-`, `*` are proved not to overflow and are written bare; the `wrap_*` builtins lower to the same operations marked `wadd`, `wsub`, `wmul` (`c` = 1) and are truncated to their type.

`BACKEND=native-ir tests/native.sh` builds every `tests/pass` and `bench` program this way and compares it with the C backend. Instructions executed (valgrind), `native-ir` against `native` and the C backend: sum 5.2G / 4.1G / 4.1G, sieve 7.9G / 7.4G / 7.4G; vec is slower (8.0G / 6.0G / 5.2G) because a `Vec` header is read from memory in every iteration. The IR path covers all of `sum`, `sieve` and `vec`, and a few functions of `utf8` and `der`; 1155 of the 1232 functions of `bastioc1` come from the IR (the places, `Str` and Vecs of several-word elements account for the gain); `--backend native-ir` builds a compiler that compiles itself to the assembly the C-built one writes (checked by `tests/native.sh`). The rest take host handles (`Host`, `Child`, `Serial`), return something other than a scalar, buffer, struct or enum, or use a few builtins.

## Emitting AArch64

`stage1/irarm64.bastio` is the second emitter, reached with `bastioc1 --arch aarch64 --backend native` (hosted target, a program whose `main` takes no parameters). It uses the same lowering and allocator as the x86-64 emitter; there is no older generator for AArch64 to fall back on, so a function the IR does not cover stops the build and the message says which function and why. The convention is AAPCS64 as far as words go: up to eight argument words in `x0`-`x7` in the order of the IR (a buffer is its data address, then its length), a result of one or two words in `x0` and `x1`, a result of more words written through the address in `x8` (the caller's frame slot). The allocator is given `x19`-`x27` and `x12`-`x15`; `x0`-`x11`, `x16` and `x17` are the emitter's. The hosted runtime (print, allocation, growing a `Vec`) is assembly over the C library, as on x86-64, and part of the trusted base. `tests/aarch64_native.sh` builds every `tests/pass` and `bench` program the emitter covers and compares it with the C backend under `qemu-aarch64`; the rest are reported as skipped, and the list shrinks as the IR covers more (tracked in #124).

## What this does not change

The verifier, the checker and the C backend. Ghost code is erased before lowering, as it is before C generation, so nothing the IR contains was ever unproved. The trusted base does not grow: the backend is already trusted to translate faithfully, and the IR is an internal form of the same translation. (The C compiler leaves the trusted base only when native is the default, #129.)

## Open questions

- Whether the AArch64 work starts from the first IR subset or waits for scalar replacement; the first is faster to a running program, the second avoids a second round of emitter changes.
- Whether SSA is worth building for #127, or whether value numbering over blocks and a liveness-based dead-store pass are enough for the loops BastiOS spends its time in. The benchmarks above say what is left on the table; the answer should come from where the remaining instructions are, not from the textbook.
