# The IR between the checker and the native backend

Status: the data, the lowering of the first subset and a text form exist (`stage1/ir.bastio`, `stage1/irdump.bastio`, golden tests in `tests/ir`), a register allocator for it (`stage1/irra.bastio`, golden tests in `tests/ra`) and an x86-64 emitter (`stage1/irx86.bastio`, behind `--backend native-ir`); the default backends do not use it yet. Tracks [#125](https://github.com/yukikotani231/bastiolang/issues/125), and is the base of #126 (register allocation), #127 (optimizations), #128 (vectorization), #124 (AArch64) and #129 (native as default).

## Why

`stage1/x86.bastio` (about 9,600 lines) writes assembly in one pass over the checked tree. Everything it knows about a value, it decides while walking: whether a variable lives in a register (`x86_assign_regs`, a pre-pass over the tree that counts uses), where a struct's words sit, what is left in `%rax`. A peephole pass cleans up after it. The items still open in the ROADMAP's native-backend entry (results built in registers, struct fields in registers, more argument registers, vectorization) all need to ask questions of the whole function (which values are live together, which loads repeat, which stores are dead), and a tree walk that has already written text cannot answer them.

Measured today (valgrind instructions, native over C, ROADMAP "Performance"): sieve 1.00, tree 1.17, utf8 1.33, vec 1.26, der 1.21, sum 1.24. The remaining gaps are exactly the ones above.

## Shape

One IR function per Bastio function instance (after `mono`), after verification, with ghost code (`spec`, `ghost`, `assert`, `requires`/`ensures`, loop invariants) already erased. Three-address code on virtual registers, in basic blocks:

- **Values** are 64-bit virtual registers (`v0`, `v1`, ...). Every sized integer is kept widened to 64 bits with its type's width recorded on the operation that can wrap (`wrap_add`, `wrap_mul`, casts); the proofs already guarantee that plain `+`, `-`, `*` do not overflow, so those need no normalisation. This is the one place the IR uses what the verifier proved: the backend never emits an overflow check, and now it also never emits a truncation it does not need.
- **Memory** is explicit: `load.w`, `store.w` (w = 1, 2, 4, 8 bytes) on an address that is a virtual register plus a constant. Frame slots, `Buf`/`Bytes`/`Vec` elements, `Box` and `Str` bytes are all addresses.
- **Blocks** end in `jmp`, `br v, then, else` or `ret`. `loop` and `while` lower to a header block with the exit test. `match` lowers to a `switch` on the enum tag.
- **Calls** take their arguments in virtual registers and return up to two words in registers (as today); bigger results are written through an address.
- **Not SSA at first.** Virtual registers may be assigned more than once. Building SSA (with block parameters rather than phi nodes) is a second step, taken only if the passes of #127 need it; a first allocator and constant folding work without it, and not requiring it keeps the lowering a straight walk of the tree.

Proof-derived facts are carried as annotations rather than as operations: a `load` or `store` that the proofs showed in bounds is simply a plain `load`/`store` (as in the C backend); #127 may later attach ranges and no-alias facts to values so a pass can use them.

## Scalar replacement

A struct or enum value whose address is never taken (never passed as `&`, never in an `&mut` borrow that outlives the statement, never stored through a `Buf`) is split into one virtual register per word at lowering time. Its fields are then ordinary values. Everything else stays in a frame slot. The checker already computes, for the register pre-pass, which names are borrowed or reassigned (`x86_borrows`, `x86_assigned`, `x86_lends`); the lowering reuses those answers instead of re-deriving them.

## Backends

`x86.bastio` becomes three parts: lowering (tree to IR, target independent), the register allocator (linear scan over live intervals, with the existing priorities as the first heuristics), and the emitter (IR to x86-64 text). The emitter is the small, target-specific piece, so AArch64 (#124) is the same IR with another emitter and its own allocator parameters (registers, calling convention).

## Getting there without a flag day

The backend is the compiler's largest file, covers the kernel and user targets (locks, device access, `smp_run`, the pool and page-table builtins, about 5,000 of its lines are builtins), and is compared byte for byte with stage0 by `asmdump --stage0` for the part it shares. A rewrite that has to cover all of it before anything runs would be unreviewable. So:

1. **Per-function fallback.** The new path lowers one function; if it meets a node it does not handle yet, it says so and that function goes through the existing generator. Both emit into the same assembly file with the existing calling convention, so mixed output links and runs. `difftest.sh` already builds and runs every `tests/pass` program, so each step is checked on the whole corpus.
2. **First subset:** integer and bool locals, control flow, calls of up to four words, `Buf`/`Vec` element access, structs of scalars. That is the code `bench/` measures and the part of the kernel that is not a builtin.
3. **Measure before widening.** `bench/run.sh` prints native against C; a step lands only if no `bench/` program is slower and the instruction counts do not rise. The done condition of #125 is exactly this, for all programs, with no function left on the old path.
4. **Then** builtins, `Lock`/device/SMP forms, and the removal of the old generator; stage0's native backend stays as the reference for the part it covers.

## Where it stands

`stage1/ir.bastio` has the operations, `ir_lower` (one function instance to IR, or the first reason it is outside the subset), a pass that drops code no jump reaches, and `ir_print`. `irdump FILE` prints the IR of every function of a program; `tests/ir.sh` compares it with `tests/ir/*.expected`. The subset so far is integer, bool, `Buf` and `Bytes` parameters, locals and results (a buffer is two registers, data address and length; `len`, `blen`, `get`, `bget` and `b = set(b, i, v)` / `bset` become `len` reads, `load` and `store` in place); arithmetic, comparisons, `&&`, `||`, `!`, unary `-`; `let`, assignment to a variable, `if`, `while`, `return`, and calls of non-generic functions of the same kinds. The `wrap_add`, `wrap_sub` and `wrap_mul` builtins lower to the plain operation (the emitter truncates to the type). `alloc`/`balloc`, `free`/`bfree`, `print`, `cast[T]` and `wrap[T]` lower to `alloc`, `free`, `print` and `wrap` (a `cast` is a `mov`: it is proved to fit). The `sieve` and `sum` benchmarks lower completely. Structs are split into registers (scalar replacement): a struct value is its fields' words in consecutive registers, so literals, field reads, field assignment, struct parameters and results of up to two words need no memory. A `Vec` of one-word elements lives in a three-word header (length, capacity, data address) in memory, in a frame slot (`slot`) or in the caller's (an `&mut Vec` parameter is its address; a `Vec` or `&Vec` parameter arrives as three words and is stored into a slot). `vec_len`, `vec_get`, `vec_set`, `vec_push` (with `vgrow` when full) and `vec_free` lower to header loads, element loads and stores. The `vec` benchmark lowers completely. An enum is its tag then the words of its largest payload, in consecutive registers like a struct; variants, `is` and `match` (the scrutinee is copied, a binding copies the payload) lower to tag compares and branches. A struct or enum lent by `&mut` (or by `&` when it takes four words or more) stays in memory as a *place* (a base register and a word offset, in the layout of `x86_words`): scalar, buffer and Vec fields are loaded and stored where they are used, nested structs are places again, and a field is lent on by address. A struct that arrives in words but has a Vec in it is stored to a frame slot and is a place there. A `Str` is held like a `Bytes`: `slen`, `sget`, literals (`str`, sharing the generator's string table), parameters, results and fields. A result of more than two words (a Vec, a wide struct or enum) goes through space the caller reserves: `ret regs a, b, ...` writes the words held in registers (a wide struct or enum built in place) straight to it, `ret mem` copies them from an address (a Vec), `callm` leaves it in a frame slot. Vecs of elements of several words (`vec_get`, `vec_set`, `vec_push`, `vec_pop`, `vec_swap`) are read and written as places at the data address plus the index times the element's words. A `&mut Buf` or `&mut Bytes` parameter arrives as the address of the buffer's two words (length, then data): the function loads them into registers on entry and writes them back before every return, since it may replace the buffer; a caller that lends a buffer puts its two words in a frame slot and reads them back after the call. `set` and `bset` (`bset(&mut b, i, v)`) store into the buffer in place. Generic enums, structs and functions lower as the instances the monomorphizer made: `Option[u64]::Some(x)`, `Pair[A, B] { .. }` and `f[T](..)` take the instance of their type arguments. `bcopy` is one `copy` (the two addresses and the byte count; the x86-64 emitter writes it as `rep movsq` for the whole words and `rep movsb` for the rest, the AArch64 one as a byte loop), and `bfrom` allocates the bytes and copies the literal into them the same way. `store_le16`, `store_le32`, `store_le64` and `load_le16`, `load_le32`, `load_le64` of core/endian.bastio are recognised by the shape of their bodies (two `bset`s of the low and high byte, or two calls of the next narrower function for the halves; a function of the same name that does anything else is lowered as written) and become one `store` or `load` of 2, 4 or 8 bytes at the byte address (index 0), which both emitters write as one instruction (the machines are little-endian). A loop `while i < n { bset(&mut b, i, v); i = i + 1; }` (just those two statements, `n` a variable or literal and `v` a variable, a literal or a `cast` / `wrap` of one, neither changed by the loop) is one `fill` of the bytes `i .. n` of `b` with the low byte of `v`, then `i = n`, when `i < n` on entry (the x86-64 emitter writes `rep stosb`, the AArch64 one a byte loop). With `bget(s, i)` for `v` (`s` another buffer) it is one `copy` of the bytes `i .. n` of `s`, then `i = n`. A struct with a Vec in it (`Bits`, a hash map) is kept in a frame slot as a place: a literal is built there, a `let` copies into a slot of its own, and as a result it goes through `callm` / `ret mem`. The console is two operations: `serial_write(con, b)` is `putc` and `serial_read(con)` is `getc`, both calls of the runtime's `bst_rt_putc` / `bst_rt_getc`, and a `Serial` parameter is one word. An enum the registers cannot hold (a Vec or a large struct in it) is kept in memory like such a struct: a variant is built in a frame slot (tag, then payload), and `match` on one that lies in memory reads the tag and binds the payload as a place (or loads it, for a scalar or buffer). `q.b = set(q.b, i, v)` stores into the buffer a field holds. A struct or enum held in registers can be lent by `&mut`: its words go to a slot and are read back after the call, as a lent buffer's are. `irdump` takes `--lib DIR` more than once, `--user` / `--kernel`, and `--where` (the source line each skipped function stopped at), so the coverage of a kernel can be counted. A `Box[T]` is one register, the address of its allocation: `box` evaluates the contents, allocates and copies them in, a field through a box is a field of the struct it points to, and `unbox` copies the contents out and frees. The `tree` benchmark now lowers completely. A `&mut` scalar parameter is lent by the address of its word: the function loads it into a register on entry and stores it back before every return, a caller's variable goes to a one-word slot for the call and is read back, and a scalar field in memory goes by its own address. The same holds for a `Box` lent by `&mut`, for a field of a struct held in registers or reached through a `Box` (its registers, or its place, are what the callee gets), and `set` can initialise a `let` (it gives the buffer back); a generic call can stand as a statement. The kernel's one-word handles (the zero-sized capabilities `Ports`, `MmioSpace`, `Mmu`, `Cpu`, and the words naming a frame, a table, a DMA window or a page) are carried like integers, a `&mut` one like a `&mut` scalar. `pt_has`, `pt_writable`, `pt_accessible`, `frame_read`, `frame_read8`, `frame_write` and `frame_write8` are plain loads and stores at the table's or frame's address (page-table entry bit 0 is present, bit 1 writable, bit 10 hidden-and-owned). `pt_borrow`, `pt_put`, `pt_put_shared`, `pt_take`, `pt_shared` and `pt_set_access` edit entries in place (an entry's address mask is `0x000FFFFFFFFFF000`; bit 9 marks a shared page); `pt_borrow` calls the runtime's page lookup. A `Pool` is `Bytes`-shaped (page count, then base address), and `pool_size`, `pool_take`, `pool_give`, `pt_new`, `pt_free` and `frame_id` use three more operations: `rt` (call a runtime helper by symbol, argument and result in the accumulator), `global` (address of a runtime symbol) and `zero` (clear the page at an address). Device accesses are four more operations: `devr` and `devw` (a volatile load or store of 1, 2, 4 or 8 bytes at an address, never dropped or reordered), and, in the kernel, `in` and `out` for the port builtins; hosted, a port is the 32-bit cell of the runtime's simulated port array and the MMIO window is 1 MiB of bytes, as the C prelude simulates them. A `PortIo` or `Mmio` is held like a `Bytes` (its base and size), `port_claim` and `mmio_claim` build one (the kernel's `mmio_claim` first calls the runtime check that the window is not RAM, through `mmchk`), a `Dma` is the page's address, and `dma_lend` / `dma_take` are a `fence` around a move, and `bytes_to_dma` / `dma_to_bytes` bracket their `copy` with `fence dma` on AArch64 (`dmb osh`, as the C prelude has it; x86-64 DMA is coherent and its IR has no such fence). `pt_lease_count` reads the runtime's array of 32-bit lease counts (indexed by the table's page number), and `bytes_to_frame`, `bytes_to_dma`, `frame_to_bytes` and `dma_to_bytes` are `copy` too, and `bmove` is a `copy` or, when the destination starts inside the source, a backward byte loop. Shared pages keep a 32-bit reference count per page number in the runtime's array: `shared_new` stores one, `shared_dup` and `pt_dup_shared` add one with `lockinc`, and `shared_drop` subtracts one with `lockdec` (which says whether it reached zero) and returns the page number or all ones. `cpu_tsc` is `tsc`, `boot_info`, `boot_acpi`, `cpu_count`, `cpu_get`, `cpu_idle` and `vec_try_reserve` are `pcall` (a call of the platform's C function or the runtime's routine that `c` names, so a call to the allocator), `box` and `atomic_new` allocate with `alloc~` (the runtime's `bst_rt_alloc_raw`: `malloc`, not `calloc`, because every word is written next; on `tree` this takes native-ir from 8.27G to 6.64G instructions), `try_alloc` and `try_balloc` are `alloc?` (the length register is the request, or zero when the data address is zero), `pool_take_dirty`, `dirty_id` and `dirty_zero` are the pool and `zero` operations without or with the clearing, and `frame_copy`, `shared_copy` and `dirty_fill` are `copypage`. An `Atomic[T]` of an integer or bool is the address of one heap word: `atomic_load` is a plain load, `atomic_store` and `atomic_swap` are `xchg`, `atomic_cas` is `cas`, and `atomic_wrap_add` is a `cas` loop whose sum wraps at the width of T (the type is read from the parameter's declaration, so an atomic that is not a parameter, or that holds a struct, stays on the fallback). `locked(l, f, args..)` evaluates the arguments, takes the lock word with `lockacq` (a spinning `xchg`), calls `f` with the address of the payload (the word after the lock word) and stores zero to release. The system calls of a user program (`sys_wait`, `sys_kill`, `sys_info`, `sys_yield`, `sys_getpid`, `sys_ps`, `sys_poweroff`, `sys_call`, `sys_send`, `sys_recv`) are `pcall` too (`c` 10 and 11): the first register is the call number, the second the address of a frame slot that holds the three argument words for `%rdi`, `%rsi` and `%rdx` (`sys_send` and `sys_recv` pass the buffer's data address and length), and 11 writes out the console buffer first, as the generator's `bst_rt_fsys` does; `sys_spawn` is `pcall` 12 on the name's data address and a slot with its two bounds. On the hosted target the twelve calls on the process are `pcall` too (`c` 20 to 31): `Host` is carried like an integer, a `Child` is three words like a small struct (pid, input, output), and a call passes the address of a four-word frame block holding the values for `%rdi`, `%rsi`, `%rdx` and `%rcx` of the runtime's routine, which writes `%rax`, `%rdx` and `%rcx` back to the block (`host_read`, `host_env` and `child_read_line` lend the buffer the routine replaces by the address of its two words, and it is read back after the call). With them, every function of `bastioc1` is written from the IR, and `bastioc1` built that way builds itself to the same assembly. A struct of more than 64 words passed by value is copied word by word like any other (the loops stopped at 64 before). Not yet: `main` of the kernel (`smp_run`). The IR is not in SSA form and has no blocks as such, only labels; the register allocator and the emitter come next.

## Register allocation

`stage1/irra.bastio` splits the instructions into basic blocks, computes liveness by backward dataflow (the registers are not in SSA form, so a register assigned in a loop is live around the whole loop), gives each register one interval from its first to its last position, and runs a linear scan over the intervals in order of start. There are two pools: callee-saved registers, which survive calls, and caller-saved ones. An interval that is live across a call (`call`, `alloc`, `free`, `print`, `vgrow`) takes a callee-saved register; any other takes a caller-saved one first. When both pools are full, the register with the lowest cost among those holding a machine register the new one may use gives it up if it costs less than the new one; otherwise the new one goes to a frame spill slot. The emitter keeps a few registers for itself, so the pools handed to the allocator are the rest. A register's cost is the number of its reads and writes, each counted 8 times more for every loop around it (a loop is the stretch from a label to a jump or branch back to it, at most 4 deep), so an inner-loop counter keeps its register over a value that is only used outside the loop. In `vec`, where `fill` and `sum` are inlined into `main`, this takes the native-ir time from 1.06 s to 0.88 s (the generator: 0.90 s); `tests/ra.sh` shows how often the allocator spills over the corpus. `ra_valid` recomputes the intervals from the instructions and checks that no two registers that are live together share a machine register and that none that is live across a call sits in a caller-saved one; `tests/ra.sh` runs it over `tests/pass`, `bench` and `core`.

## Passes

`stage1/iropt.bastio` holds the passes that run between the lowering and the allocator. The first is scalar replacement of frame slots (`iropt_slots`): a `slot` whose address is only the base of one-word `load`s and `store`s at constant indices is dropped, each of its words becomes a virtual register of its own, a `store` becomes a `mov` into it and a `load` a `mov` out of it. A `Vec` parameter, which the lowering stores to a slot so the `vec_*` forms can address its header, then keeps its length, capacity and data address in registers instead of reading them from the frame at every `vec_len` and element access. A slot whose address goes anywhere else (a call, `vgrow`, `ret`, arithmetic, a store) stays in memory. The second pass is copy propagation (`iropt_copies`): in `d = mov a` where `d` and `a` are each written once, every read of `d` becomes a read of `a` and the `mov` is dropped (the word registers the first pass creates for a parameter are the main case). It does so only when `a` keeps its value until the last read of `d`: `a` is a parameter, or its definition lies before the `mov` with no label between that definition and the last read of `d`, so a loop that re-runs the definition or skips the `mov` blocks it. The third is jump threading (`iropt_thread`): when `br r, T, F` leads to a label whose first instruction is `br r, T2, F2` on the same register, the outcome is known on that edge and it goes straight to T2 or F2 (the second test that `&&` and `||` leave after materialising their result). Dead code elimination (`iropt_dce`) follows copy propagation: a pure instruction (no effect, no division) is dropped when no instruction reads its result, or when the same straight-line run overwrites the result before any read (the lowering leaves `v = const 0` then `v = mov x` when it fills a result tuple). The lowering also turns the condition of an `if` or `while` into branches directly (`ir_branch`): `&&`, `||` and `!` of booleans become chains of `br` with no materialised result. The lowering itself binds a `let` of an integer straight to the temporary the initializer made instead of copying it. Before these runs inlining (`stage1/iropt_inline.bastio`, `iropt_inline`): a `call` or `callm` of a function that lowers, is not the function itself and has as many parameter words as the call has arguments is replaced by the callee's instructions (itself run through the three passes) when the callee has at most 40 instructions, or at most 160 when the call lies in a loop. The callee's registers, labels and argument positions are shifted past the caller's, its parameters become `mov`s from the argument registers, and each `ret` becomes moves into the call's result registers (for a `callm`: one-word stores into the frame slot it named) and a jump to a label after the copy; so a struct or enum that the callee builds in registers stays in registers at the call site. A body that only computes with registers (constants, moves, arithmetic, comparisons and branches: a predicate such as `n == 3 || n == 7`) is inlined up to 120 instructions whatever the size of the caller, since once the switch pass has run it is a few compares. A callee with a single call site in the whole program (`iri_count` lowers every function once to count them; x86-64 only) is inlined up to 150 instructions into a caller that has not yet reached 3000; larger bodies there made the passes after inlining take ten times as long on the BastiOS kernel. A function is also inlined into itself, in each of the first two rounds and only if it has at most 80 instructions (the copy keeps its own recursive calls): a recursive builder that makes two calls then takes four levels of its own body, which on `bench/tree` saves most of the calls and frames (5.89G to 5.62G instructions, the C twin: 5.54G; `bench/der` -4%, `bench/queens` -2%). A third round made it worse (6.02G). Copies are scanned again for calls, three rounds deep. `irdump --opt FILE` prints the IR after the passes; `tests/ir/NAME.opt.expected` is compared by `tests/ir.sh`. Both emitters (x86-64 and AArch64) run the passes, inlining included. `iropt_range` fuses the two tests of `x < a || x > b` (or `a <= x && x <= b`: two unsigned compares with constants that send the values outside `[a, b]` to one place) into `t = x - a; t > b - a`, and the x86-64 emitter writes the subtraction into another register as one `lea`; on `bench/utf8` this and a copy propagation that now also crosses loops (a name for a register written once outside every loop) take native-ir from 4.45G to 4.30G instructions (the C twin: 4.19G). `iropt_ifconv` (x86-64 only, before the induction-variable and value-numbering passes) turns an `if` or `if`/`else` into straight-line code when each arm is at most eight instructions that only compute registers (no load, store or call; a division only by a nonzero constant), the condition is a comparison, and the arms write at most three registers that something outside them reads: both arms run into fresh registers and each result is selected with the mask `-c`, `r = e ^ ((t ^ e) & -c)`. A branch whose outcome depends on data (a bit of the previous value in a CRC step) is mispredicted about half the time, which costs far more than the dozen instructions that replace it; `bench/crc` on native-ir goes from 0.33 s to 0.15 s (the C twin: 0.10 s). An arm that only adds a constant to a register it reads (`n += 1`) becomes `n = n + flag` (or `n + (K & -c)`) with no select. An arm with a `load` converts only if the loads cannot fault (the proof already covers the index) and nothing the arms write is read by the arms themselves: a test of data such as the next cell of a Life grid then costs no misprediction, while a predictable `if` around a hash-table probe stays a branch. `iropt_cmpfuse` first joins `a || b` and `a && b` of two comparisons into one branch (`or`/`and` of the two flags, with the at most six pure instructions between them run unconditionally), but only where one side is a short non-empty arm that `iropt_ifconv` can then take; error checks with two well-predicted branches stay as they are. `bench/life` goes from 89 ms to 70 ms (the C twin: 55 ms). `iropt_zext` (before `iropt_ifconv`) finds an upper bound for every register by iterating over the function (the arguments, calls and loop-carried values that keep growing are unbounded) and turns `x % k` and `x & (2^n - 1)` into a copy where the bound is already below the modulus or mask; `iropt_xorcancel` (after the value numbering) turns `(e ^ k) ^ e` into `k`. Together they take the reduction out of a CRC step, and the select `r = e ^ ((t ^ e) & -c)` becomes `r = e ^ (k & -c)`: `bench/crc` goes from 0.15 s to 0.095 s (the C twin: 0.10 s). `iropt_accrec` (on the lowered function, before the inlining) turns `return t + f(a)` with a wrapping add into `acc = acc + t; params = a; goto top` and every other `return v` into `return v + acc`: `fib(n - 1) + fib(n - 2)` makes one call instead of two, and the body copied in by the self-inlining rounds brings the other back, so `bench/fib` goes from 44 ms to 30 ms with five rounds of self-inlining (the C twin: 18 ms). `ix_incr` (x86-64, just before the allocator) turns `t = x + K; ...; x = mov t` into `x = x + K` at the copy when every other read of `t` lies in between, so the `x + 1` that a loop body uses for a neighbour and the counter's step no longer share a register that lives to the end of the loop; and a select of 1 or 0 by a condition (`v = 0; if c { v = 1 }`) is the 0/1 flag itself, not a mask made from it. `ix_ivmerge` makes one register of two counters that start equal and step side by side (the index of a load and of a store in one row). Together they take `bench/life` from 71 ms to 62 ms. `iropt_punroll` unrolls an innermost counted loop with a small body by two or four when the induction variable is only read, rewriting each read as `x + m*step` so the address folds into displacements; `bench/matmul` reaches the C twin. A value the allocator left in the frame that a result of more than two words returns only as one and the same word is kept in that word of the result area (`ix_result_homes`), so the store at the `ret` is already done; the native build of `bastioc1` runs 0.9% fewer instructions. A function that first tests its parameters and, when they pass, returns a value computed from them (no load, store, call or division on that path) is entered through a stub (`ix_fast_entry`): the test and that return, compiled as a function of their own with no frame and no saved registers, in front of the function proper, which a failed test jumps to with the argument registers untouched. Only functions with at most four register parameters qualify, the stub is dropped if its code before the jump to the function proper writes an argument register, and it is used only where the function proper saves four or more callee-saved registers (the stub costs a compare and a jump on every other entry). The early return of `bench/fib` then no longer saves and restores six registers: 31 ms to 24 ms (the C twin: 16 ms). `iropt_entry_guard` (x86-64, after loop rotation) drops the test at the top of a loop that nothing but the fall-in reaches when the counter was just set to a constant below a constant bound, so `i = 0; while i < K` enters its body without the compare; and a function whose allocation counted a callee-saved register that no instruction ended up using is allocated again with one register fewer, so it no longer saves and restores it (`bench/crc` 538M to 521M instructions, an open-addressing hash table 86.9M to 79.1M). `iropt_ifconv` leaves a branch alone when the conversion would cost more than eight instructions on every pass (the arms' computations, not constants or copies, plus three per selected register): an arm that does real work is usually a rare path such as a bounce at the edge of a range, which the predictor handles, and `bench/particles` goes from 477M to 267M instructions (the C twin: 226M). On x86-64, `t = load p[k]; u = t op x; store p[k], u` of a whole word (`op` one of `add`, `sub`, `and`, `or`, `xor`, `x` an immediate or a register, `t` and `u` read once) is one instruction on memory (`ix_rmw`: `addq $1, (%r8,%r10,8)`), and a shift by a variable count shifts in the result register instead of `%rax`; `bench/radix` goes from 119.8M to 98.8M instructions (the C twin: 94.6M). Inside a counting loop `L: t = lt i, K; br t, B, E`, `iropt_zext` also bounds the values made from the counter (`iropt_zext_loops`): up to the first write to the counter, where the region is entered only from the loop test, `i` is below `K`, so `(i*8 + k) % m` and a mask of it vanish when that bound is already below `m`; `bench/bfs` goes from 458M to 391M instructions (the C twin: 377M). The retry without an unused callee-saved register (`irx_shrink`) is kept only if it spills no more than the attempt before it: the register that came out unused was held by a value that never reached the text, and taking it out of the pool pushed a loop counter into the frame (`bench/uf` 169.5M to 163.2M instructions, `bench/vm` 810M to 756M; the C twin of `uf`: 151.4M). The same holds for a `load` that only a wrapping `add`, `sub`, `and`, `or` or `xor` reads when no normalising wrap follows (`add (%rbx,%r11,8), %r12`): `bench/fenwick` goes from 333.7M to 312.7M instructions (the C twin: 312.7M). A rotation of a 32-bit word, `wrap[u32](x << k) | (x >> (32 - k))` (the shifts in either order, each result read once, `x` proved below 2^32 by `iropt_ub_all`, the bound pass that `iropt_zext` uses, which also takes the width of a `wrap` or sized wrapping operation as a bound), is `roll $k` (`ix_rot32`); when the word was made by an `xor`, `or` or `and` whose other operand is the register the rotation overwrites, that op is done in place in front of it. `bench/chacha` (the quarter round on four u32 words) goes from 789M to 252M instructions (the C twin: 235M). A division by a constant that is not a power of two uses the multiplier that needs no shift of the dividend first when one exists (`ix_div_magic`: for 10, `mulq` by `0xCCCCCCCCCCCCCCCD` and `shr $3`, the quotient left in `%rdx`), and `iropt_remdiv` rewrites `a % K` as `a - (a / K) * K` where an `a / K` of the same register appears in the function, so that the value numbering shares one multiplication between them in a digit loop (`bench/itoa` 1.51G to 1.26G instructions; the C twin: 1.05G). `iropt_ivs` also reduces the multiples of a counter that counts down (`t = k - c; k = mov t`: the new register is stepped with a `sub`), and `iropt_ebb` runs once more ahead of it, with a table of the copies of a register that is written more than once (valid until that register is written), so that the address of `a[j - 1]` read in the test of an insertion-sort loop and again in its body is one register that the loop steps by 16; the `t = k - c` of a counter's step is not turned into a copy, and an unsigned `x > 0` or `x <= 0` after an `add` or `sub` into `x` is a test of the flags that instruction set (`sub $1, %r10; jne`). `bench/records` goes from 253M to 169M instructions (the C twin: 135M), `bench/sort` from 538M to 471M. `iropt_rotate` also takes a test that adds before it compares (`while i + 12 <= n`). A byte `load` that only an `eq`/`ne` with the byte loaded just before reads is `cmpb mem, %reg8` (`ix_ld8cmp`). `iropt_efacts` (before `iropt_ifconv`) keeps, along an extended basic block, the range that the branches on a comparison of a register with a constant give (`k < 12` on entering the body of `while k < 12 && ..`) until the register is written, and sends a branch whose target begins with a test of that register against a constant (the `if k == 12` after the loop) straight to the side the range decides; `bench/strfind` goes from 3.05G to 2.17G instructions (the C twin: 2.15G). `iropt_ebb` also reads the base of a `load` or `store` through the register it was copied from; `iropt_ivs` reduces `k - n` (a counter less a register that the loop does not write) when only an index reads it, so the loop steps one more register instead of copying and subtracting for every access; and a word `load` that only a comparison reads is moved down to that comparison (`ix_sinkld`), which reads it from memory (`cmpq mem, %reg`, either side). `bench/knap` goes from 1.02G to 0.82G instructions (the C twin: 0.72G), `bench/heap` from 339M to 322M. A byte `load` that a comparison reads against a register holding a byte (`ub` below 256) is `cmpb mem, %reg8`, and `iropt_rotate` copies a run of tests with one exit (`while a && b && c`) together, a label of its own between the copies, so such a loop has no jump back to its first test; `bench/rle` goes from 1.92G to 1.67G instructions (the C twin: 1.69G). The `sub` of a constant that feeds the add of a multiply-add pair (`cur * 10 + (c - 48)`, the `lea` pair of `ix_scale_fuse`) is not written: the last `lea` takes the constant as its displacement (`lea -48(%rbx,%r10,2)`); `bench/parse` goes from 1.73G to 1.61G instructions (the C twin: 1.40G). A subtraction whose result register is its subtrahend's (`r = v - r`, the remainder `v - (v / 10) * 10`) is `neg r; add v, r`, not a move through `%rax`: `bench/itoa` 1.26G to 1.22G instructions (the C twin: 1.05G). A rotation also counts its word as below 2^32 when the right shift is typed `u32` (a `Vec[u32]` element, whose load carries no width), the `wrap` of a `u32` is one `movl r32, r32`, and a `u32` `add`, `sub` or `mul` with a spilled operand is a 32-bit instruction on memory; `bench/sha256` (the compression function on a schedule in a `Vec`) goes from 3.61G to 2.09G instructions (the C twin: 1.61G). A division or remainder by a constant inside a loop no longer loads its multiplier (`movabs`) on every pass: `ix_divhoist` (last of the passes before the allocator) makes the multiplier a register of its own in front of the innermost loop around the division (or, for a rotated loop, in front of the entry test that jumps into it, when only a stretch with no label lies between the two), records it in the division's `c` (the register plus two, read by `ra_reads`), and the emitter writes `mul %reg`; `bench/vec` goes from 5.60G to 5.20G instructions (the C twin: 5.40G), `bench/itoa` from 1.22G to 1.15G (the C twin: 1.05G). `iropt_ivs` folds `a[k - c]` (or `a[k + c]`), when it is only an index of `load`s and `store`s of one base that the loop does not write and `c` is not written either, into `b[k]` with `b = a - c*size` made in front of the loop (`iropt_ivs_fold`), so the loop steps no register for the offset index and the two accesses share one (`bench/knap`: 0.82G to 0.72G instructions, the C twin: 0.72G). On hosted and user targets (not the kernel, which does not enable SSE), two adjacent word loads from one base and the two stores of them to adjacent words of another (the copy of a two-word struct) become one `IR_CP16`, `movdqu` through `%xmm0` and `movups` (`ix_copy16`; the second load must be read only by the second store, the first load stays if a comparison reads it, and nothing between the loads and the stores may write memory or the base); `bench/records` goes from 169M to 135M instructions (the C twin: 135M).

## Emitting x86-64

`stage1/irx86.bastio` is the emitter, reached with `bastioc1 --backend native-ir` (not listed in `--help`; the hosted, user and kernel targets). `x86_program_ir` is `x86_program` with one difference: each function is lowered, and a function the IR covers is written from the IR and its allocation; any other goes through the generator of `x86.bastio`, into the same file with the same calling convention, so the two kinds call each other. The convention is the generator's: up to four words of arguments in `%rdi %rsi %rdx %rcx` counted from the last parameter's first word (more are pushed, the last parameter nearest the return address), a result of one word in `%rax` and of two in `%rax:%rdx`, `%r8`-`%r11` clobbered (the callers save theirs), `%rbx` and `%r12`-`%r15` preserved. A `Buf` or `Bytes` is (length, data address) there and (data address, length) in the IR, so the emitter swaps the two at parameters, arguments and results. A function whose parameters or calls disagree with the generator's word counts, or with more than 40000 instructions, stays with the generator.

The allocator is given `%rbx %r12`-`%r15`, `%rbp` (see the frame below) and `%r8`-`%r11`; `%rax %rcx %rdx %rsi %rdi` are the emitter's, so no value shares a register with an argument. Registers written once, by a constant, get no register and are used as immediates (`ra_alloc_const`); a register may take the machine register of one whose last use is the instruction that writes it, because the emitter reads every operand before it writes. The emitter also copies a temporary into its variable directly (`t = op ...; s = mov t`), divides by a constant as the generator does (`x86_div_const`), repeats a loop's test at its end, and fuses a comparison with the branch that alone reads it. Plain `+`, `-`, `*` are proved not to overflow and are written bare; the `wrap_*` builtins lower to the same operations marked `wadd`, `wsub`, `wmul` (`c` = 1) and are truncated to their type.

The frame. The emitter writes every frame word as `N(%fp)`, a pseudo-register. When the function body has `%rsp` change only by `push`, `pop` and `add`/`sub` of a constant, and every label, jump and return sits at push depth zero, `ix_fpo` rewrites each `N(%fp)` to `N + frame size + depth (%rsp)` and `leave` to an `add`, so the function has no frame pointer and `%rbp` is a sixth callee-saved register for the allocator. A body it cannot follow is generated again with five registers and the classic `push %rbp; mov %rsp, %rbp` frame (`irx_function`). A parameter that arrives on the stack and that the allocator leaves in the frame stays in its argument word. After the body is written, `ix_flip_jumps` turns `jCC .La; jmp .Lb; .La:` into `jNCC .Lb`. The allocator first runs as above; a register it left in the frame is then split around a call-free loop that reads or writes it at least six times (`ra_split_loops`): a fresh register is used inside the loop, copied in on the way in and out on the way out when the loop writes it, and allocation runs again. This is what lets a scan loop keep its counter in a register when a hotter loop elsewhere held every register for the whole function. Measured on the BastiOS kernel with `bench/run.py --icount`: instructions per system call 2506 before these, 2360 after, against 2278 for the C backend.

`BACKEND=native-ir tests/native.sh` builds every `tests/pass` and `bench` program this way and compares it with the C backend. Instructions executed (valgrind), `native-ir` against `native` and the C backend: sum 5.2G / 4.1G / 4.1G, sieve 7.9G / 7.4G / 7.4G; vec is slower (8.0G / 6.0G / 5.2G) because a `Vec` header is read from memory in every iteration. The IR path covers all of `sum`, `sieve` and `vec`, and a few functions of `utf8` and `der`; 1155 of the 1232 functions of `bastioc1` come from the IR (the places, `Str` and Vecs of several-word elements account for the gain); `--backend native-ir` builds a compiler that compiles itself to the assembly the C-built one writes (checked by `tests/native.sh`). The rest take host handles (`Host`, `Child`, `Serial`), return something other than a scalar, buffer, struct or enum, or use a few builtins.

## Emitting AArch64

`stage1/irarm64.bastio` is the second emitter, reached with `bastioc1 --arch aarch64 --backend native` (hosted target, a program whose `main` takes no parameters). It uses the same lowering and allocator as the x86-64 emitter; there is no older generator for AArch64 to fall back on, so a function the IR does not cover stops the build and the message says which function and why. The convention is AAPCS64 as far as words go: up to eight argument words in `x0`-`x7` in the order of the IR (a buffer is its data address, then its length), a result of one or two words in `x0` and `x1`, a result of more words written through the address in `x8` (the caller's frame slot). The allocator is given `x19`-`x27` and `x12`-`x15`; `x0`-`x11`, `x16` and `x17` are the emitter's. The hosted runtime (print, allocation, growing a `Vec`) is assembly over the C library, as on x86-64, and part of the trusted base. `tests/aarch64_native.sh` builds every `tests/pass` and `bench` program the emitter covers and compares it with the C backend under `qemu-aarch64`; the rest are reported as skipped, and the list shrinks as the IR covers more (tracked in #124). Words beyond the eighth go on the stack at `sp` (the callee reads them at `x29 + 16 + 8 * (k - 8)`). The runtime also has the console (`putc`, `getc`), the allocation routines, `vec_try_reserve` and the host and child calls, and a `main` that takes only host capabilities gets them from `argc` / `argv`. `bastioc1` built this way for AArch64 writes the same C for its own source as the x86-64 build; `tests/aarch64_native.sh` checks it.

## Emitting WebAssembly

`stage1/wasm.bastio` is the third emitter, reached with `bastioc1 --arch wasm32 -o prog.wasm` (hosted target; `main` or `export fn`s). It lowers each function with the same IR and runs the machine-independent passes the AArch64 emitter runs (`a64_passes`), but there is no register allocation: every IR register is an `i64` local and every word an `i64`, and an address is a 32-bit offset into the one linear memory, held zero-extended. A function's parameters are its first locals, then the registers, the segment number (`i32`) and the frame base.

Control flow. The instructions between two labels are a segment. A function with labels is one `loop` around nested `block`s with a `br_table` over the segment number at the top; a jump sets the segment number and branches to the loop (`select` picks the target of a conditional branch). A function without labels is straight-line code.

Memory. The shadow stack grows down from 1 MiB and holds the frames' `IR_SLOT`s and the slots of calls with big results; the string literals sit from 1 MiB; the heap follows. The allocator gives power-of-two blocks behind a header word, keeps a free list per size class (heads at address 16) and takes new blocks from a bump pointer, growing the memory when it runs out; `alloc` promises zeroed memory, so a reused block is cleared. An allocation past 4 GiB traps (the `try` flavours return 0). The wasm module imports `bastio.print(i64)` (a decimal line) and `bastio.putc(i64)`; it exports `memory`, `bst_alloc`, `bst_free`, `main` (the exit code is its result) and every `export fn` under its name. Calls follow the IR: up to two result words are wasm results, and a result of more words is written through an extra last parameter that holds the address of the caller's frame slot (the counterpart of `x8` / the slot address of the other emitters). `tests/wasm.sh` builds every `tests/pass` and `bench` program the emitter covers, runs the module with `tests/wasm_run.js` under Node.js and compares output and exit status with the C backend; the rest are reported as skipped (kernel and device operations, host calls, locks).

## What this does not change

The verifier, the checker and the C backend. Ghost code is erased before lowering, as it is before C generation, so nothing the IR contains was ever unproved. The trusted base does not grow: the backend is already trusted to translate faithfully, and the IR is an internal form of the same translation. (The C compiler leaves the trusted base only when native is the default, #129.)

## Open questions

- Whether the AArch64 work starts from the first IR subset or waits for scalar replacement; the first is faster to a running program, the second avoids a second round of emitter changes.
- Whether SSA is worth building for #127, or whether value numbering over blocks and a liveness-based dead-store pass are enough for the loops BastiOS spends its time in. The benchmarks above say what is left on the table; the answer should come from where the remaining instructions are, not from the textbook.

The native-ir emitter keeps one copy of a wide constant that a loop reads (the pass that hoists it also merges it with an equal constant just in front of the loop), puts the multiplier of a division by a constant in a register ahead of the loop even when the loop is entered through a test or a cold block placed after it, and turns `x % K == 0` / `!= 0` for an odd constant `K` into a multiply by the inverse of `K` and one compare against `(2^64-1)/K`.

After the first slots and copies, `iropt_wbk` drops a `v = mov t` when `t` is written once by `t = mov v` and every path reaches the second `mov` with neither register written since (a forward walk over the paths that carries "`t` is still a copy of `v`"); a `&mut` struct that an inlined function copies back unchanged no longer costs a round trip through registers in each iteration of the caller's loop, which takes `bench/itoa` from 1.10 to 1.07 times the C twin's instructions. `irdump --inline` prints the IR after the inlining.

Two more changes to the native-ir passes: the register allocator lets the result of a two-operand instruction take the machine register of its first operand when that operand dies there (what a select by `cmov` needs to avoid a copy: `bench/lcs` goes from 1.08 to 1.00 times the C twin's instructions), and `iropt_rotate` also rotates a loop whose test computes a value the body reads again (the copy at the bottom writes the same register; a test may now contain a `%`, `/`, `*`, `|`, `^` or `<<`), which takes `bench/uf` from 1.08 to 1.06.

`ix_countdown` (after the loops are rotated): a loop `i = const c0; H: ...; i = add i, 1; t = lt i, K; br t, H, E` whose counter nothing else reads, with `K` a constant above `c0` that only the compare reads and `H` reached only by the back edge and the straight line from the `const`, counts `K - c0` down to zero (`sub`, then `gt i, 0`, which the emitter turns into the flags of the `sub`): no compare is left in the loop. `bench/chacha` goes from 1.07 to 1.00 times the C twin's instructions, `bench/bfs` from 1.03 to 0.94.

The emitter writes `t = mul a, 3|5|9` followed by `d = add t, imm` (where nothing else reads `t`) as one `lea imm(a, a, 2|4|8)` (`ix_mul_lea`): the `3 * x + 1` step of `bench/collatz` goes from 1.06 to 1.03 times the C twin's instructions.

A load or store whose index is `x - K` (K a constant, the difference read by nothing else) takes the displacement `-K` in the address, as `x + K` already did (`ix_addr_fold`, `ix_addr_fold2`): `mov -120(%r8,%r9,8)` for the element 15 before `t`. SHA-256's message schedule goes from 1.30 to 1.25 times the C twin's instructions (the rest is a loop that gcc vectorizes).

A sum, difference or product modulo 2^32 that cannot be written in the destination register (it lives in memory, or shares a register with the second operand) is one 32-bit instruction on `%eax`, with no `mov %eax, %eax` after it. The load-ALU fusion (`ix_load_alu`, a table element read once becomes the memory operand of the instruction that uses it) also takes sums modulo 2^32 and results in another register, so the `t1 + k[t] + w[t]` of SHA-256 reads both table words as memory operands: 1.25 to 1.19 times the C twin's instructions.

The facts of `iropt_efacts` also carry values a register is known not to equal (`c != 10` after the branch on `c == 10`), pass from a branch or jump to the label that edge alone reaches (not only to the block that follows it), and decide the test a jump reaches, and again from there: in `bench/wc` the second `c == 10` of `c == 32 || c == 10` after `c == 10` is no longer tested, and the count loop is 0.95 of the C twin's instructions (1.06 before).

A division by a divisor that lives in a register of its own divides by that register, with no copy into `%rcx` first. The step of Euclid's algorithm (`t = x % y; x = y; y = t`, `t` read by the last move alone) is one group (`ix_rem_swap`): the dividend in `%rax`, `div` by `y`, `x` taking `y`'s register, then `y` taking the remainder from `%rdx`, with no register for `t`. The gcd loop of `bench/collatz` goes from 12 instructions per step to 10 (C: 9), and the benchmark from 1.034 to 1.018 times the C twin's instructions.

A `jmp` to a short join is replaced by a copy of it (`iropt_taildup`, run last among the IR passes, in functions of up to 200 instructions): up to six instructions that only compute values, then a `br` or `jmp`, and when the `br` falls into a label a second run of the same kind. A register written once and read only inside the run gets a new register in the copy. The even arm of `x % 2 == 0` in `bench/collatz` no longer jumps back to the join: 1.018 to 0.964 times the C twin's instructions, and `bench/queens` from 0.998 to 0.963. Larger functions are left alone, since a copy there made the allocator spill (`bench/utf8`).

Facts about registers (`iropt_efacts`) reach further than a label with one edge. A label that two to four jumps and branches from above reach, or one that the code above falls into besides one to three jumps, keeps what every edge says: the widest of their ranges for a register, and a value that all of them leave out (a range that does not contain it counts). A loop header the code above falls into, or one jump reaches, keeps the facts about the registers that nothing in the loop writes; the loop is the code from the header to the last jump back to it, extended by a jump back to a label inside it, and a header that an edge from above enters in the middle gets none. A register that holds a constant is a range of one value, and a branch on a comparison of two registers, one of them such a constant, is decided by the facts the way one on a constant is; the side it cannot take loses an edge. In `bench/itoa` the tests `len != 0` and `0 < len` after the digit loops are decided: 1.031 to 1.019 times the C twin's instructions.

A block that branches back to its own label (`br c, then, self`) is emitted as one jump on the inverted condition back to itself and an unconditional jump out, instead of a jump out and a jump back, so going round costs one taken jump and one fewer instruction (`ix_br_flags`). The inlined levels of `bench/fib` are such loops around a call: 0.975 to 0.937 times the C twin's instructions.

A label that only a conditional branch comes back to gets its `.p2align 4` only when no instruction falls into it, so that the padding does not run on every pass of a loop whose head is entered from above.

A shift by a count held in a register copies the count to `%cl` first. In a loop that does nothing else with `%rcx` (no call, no division by a register, no second count) and never changes the count's register, the copy is made once in front of the loop (`ix_clhoist`, a pass over the text of the function): the loop is a label, the last jump back to it, and nothing from outside jumps to a label inside it. The count loop and the scatter loop of `bench/radix` lose one instruction per pass: 1.044 to 0.956 times the C twin's instructions.

A store of 1, 2 or 4 bytes keeps the low bytes of its value, so the `x % 2^k` or `x & mask` (with the low bytes of the mask all ones) that is made just before it and read by nothing else is not computed: the store takes `x` (`ix_stmask`). The byte written by `bset(&mut b, i, cast[u8](x / 65536 % 256))` no longer goes through `and $255`; `bench/fnv` goes from 1.018 to 1.000 times the C twin's instructions. A remainder by a constant whose multiplier needs the 65th bit of the dividend (61, 53, 7, ...) reads the dividend again from its own register for the last subtraction and subtracts into the result's register, in place of the two copies in `%rsi` and `%rdi` and the move back.

The multiplier of a division by a constant (`ix_divhoist`) is now made in front of the outermost loop around the division that has a place in front of it, not the innermost: a constant is the same on every pass of every loop, and a multiplier the allocator keeps in the frame is used as `mulq mem`, so holding it longer costs no instruction. Two digit loops that divide by 10 inside one outer loop share one register made once, where each made its own on every outer pass: `bench/itoa` 1.055 to 1.047 times the C twin's instructions.

The entry test of a loop is also dropped when the label in front of it is reached by one branch right above it and by falling in (`iropt_entry_guard`): the test that rotation copied for `while tmp > 0 && len < 20` leaves `len < 20` standing after `tmp > 0`, and `len = 0` before both decides it. `bench/itoa` goes from 1.047 to 1.039 times the C twin's instructions.

`iropt_efacts` also knows that `x = x + K` (a positive constant, an addition that cannot wrap) is not zero, and that a copy of such a value is not either, and it runs once more after the loops are rotated. The `len == 0` test after the digit-count loop of `bench/itoa` is decided on the edge that leaves the loop (the length was just incremented), so that edge no longer runs it: 1.039 to 1.031 times the C twin's instructions.
